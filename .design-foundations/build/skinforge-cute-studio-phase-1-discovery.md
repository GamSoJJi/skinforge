## Gaps

1. **Silkscreen floor vs. mock's small labels.** The Phase 1 plan Constraint carries forward a hard dealer pin: "Silkscreen floor 12px (7px 선례 illegible)." The reviewed mock renders `.panel-section-label` / `.viewer-label` at 9px, and one label is explicitly overridden to 8px. The mock review flagged this as a non-blocking "readability edge case" note, not a floor violation, because it never checked the mock against the 12px plan constraint. **Resolution:** DESIGN.md locks the 12px floor as specified (dealer pin, not weakened). The mock's sub-12px Silkscreen instances are flagged here as a Phase 2 fix-forward item: those specific labels must move to ≥12px Silkscreen or drop to the Nunito body stack. This is not a Phase 1 blocker — Phase 1 does not touch the mock file or component specs (both out of scope).
2. **Missing Korean-script fallback in the mock's font stack.** The mock's `--font-body: 'Nunito', sans-serif` has no CJK fallback, but the live app (`src/App.jsx`) is heavily Korean-labeled (파일, 색상, 크기, 모양, 가이드, etc.). Nunito has no Hangul glyphs. **Resolution:** DESIGN.md's body stack adds the same Korean-aware system fallback the current (Ledger Pantry) DESIGN.md already carries (`-apple-system, "Malgun Gothic", "Apple SD Gothic Neo", "Segoe UI", sans-serif`) after Nunito — this is a script-coverage fallback, not a second display/brand font, so it doesn't violate the fonts-doctrine two-family rule.
3. **Functional colors (error/success/warning/info) absent from the mock entirely.** DW-1.2 requires them as part of the complete semantic set. Resolved via `palette.mjs`'s hue-independent functional formula (confirmed identical output regardless of seed — verified by comparing this run's functional steps against the current DESIGN.md's own functional steps, which came from a different seed hue and produced byte-identical hex values), then contrast-verified against the new cream background independently (functional-11 text steps all clear 4.5:1; functional-9 solid-fill steps are documented as fill primitives whose on-color pairing is a Phase 2/component decision, consistent with how the current DESIGN.md itself treats them — it never contrast-tests its own -9 steps against page background either).
4. **Radius-scale phrasing mismatch.** The dispatch prompt's Key-Decisions bullet says "buttons/inputs/swatches: 8px minimum," but the actual reviewed-and-passed mock uses `--r-input: 6px` for the hex field, and the mock review's own DW-MOCK.2 premise explicitly required "inputs ≥6px" (a separate, lower floor than buttons/swatches ≥8px). **Resolution:** treated the mock + its passed review as the authoritative source (per the prompt's own framing: "Approved mock ... source of resolved token decisions") over the prompt's paraphrase. Radius scale locks `sm: 6px` (inputs) distinct from `md: 8px` (buttons/swatches/tooltips) — reconciles both without silently dropping the 8px floor where it does apply (buttons/swatches).
5. **Pill-shaped controls use a bare `20px` instead of a token** (mock review Minor finding). Phase 1 closes this at the token level by naming a `--radius-full` (999px, functionally pill-shaped at any of this UI's control heights) primitive so Phase 2 has a token to route the fix through instead of re-inventing one.

## Design Decisions

**Doctrine applied:** `design-dna`, `fonts`, `color` (built-in knowledge — `docs/pillar-taxonomy.md` not present in this project; proceeding per the dispatch prompt's fallback instruction).

- **design-dna**: The identity statement, "Never" list, and dealer-pin carry-forward (Silkscreen 12px floor, exact locked hex values) all serve design-dna's core discipline — a locked DNA must be internally consistent and resistant to silent drift. Rather than re-deriving colors from scratch this phase, the already-reviewed mock's exact hex values are treated as the DNA's law (per the Baseline Discipline's "law-once-locked" framing extended forward: these values were the subject of a passed design review and are pinned in the dispatch prompt's Key Decisions, so they're honored exactly, not re-rolled).
- **fonts**: Applied the "≤2 text families" rule — Silkscreen (display) + Nunito (body), with a Korean-script fallback appended to Nunito's stack (not a third family — a script-coverage necessity, same precedent the current, being-replaced DESIGN.md already used). Nunito chosen over Fredoka One per the plan's own edge-case note (Fredoka One risks being too heavy at the 12px Silkscreen-adjacent floor) and because the reviewed mock already exercises Nunito successfully at 11–13px UI-label sizes with all interactive-text contrast pairs passing (mock review DW-MOCK.3).
- **color**: Ran the WCAG 2.1 relative-luminance formula directly (`contrast-check.mjs`, scratchpad) against every locked hex pair instead of relying on `palette.mjs`'s own algorithmic derivation, because `palette.mjs --seed "#C8490D"` does **not** reproduce `#C8490D` as its own accent-9 step (confirmed by test run — it output `#cb846b` instead, since the tool solves contrast by constructing its own ramp from a seed hue, not by preserving an input hex verbatim). The locked hex values are pins from an already-reviewed mock, not a fresh derivation task, so verifying the exact pinned pairs directly is the correct tool for this job — reusing `palette.mjs` only for the functional-color scale, which *is* being freshly generated (hue-independent, confirmed identical to the current DESIGN.md's own functional steps).
- Functional colors: reused `palette.mjs`'s own functional ramp (`--error-9/-11`, `--success-9/-11`, `--warning-9/-11`, `--info-9/-11`) rather than hand-picking new ones — confirmed hue-independent by matching the current (Ledger Pantry) DESIGN.md's functional values exactly.
- Border radius: resolved the sm/md/lg scale from the mock's real, reviewed values (6/8/12) rather than the dispatch prompt's paraphrase (see Gap 4), adding a `--radius-full` token to give Phase 2 a home for the mock review's Minor "hardcoded 20px" finding.
